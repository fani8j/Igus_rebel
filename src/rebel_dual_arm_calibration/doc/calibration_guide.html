Dual-arm ReBeL calibration

Operator guide for the test-table cell: two igus ReBeL arms (arm_left on 192.168.3.11, arm_right on 192.168.3.12) and one Gemini 336 scene camera. Generated 2026-10-10.

Overview

The calibration finds two things:

  • Where arm 2 really stands relative to arm 1 (arm_right_base). MoveIt uses this to keep the two arms apart.
  • Where the scene camera is (camera_link), for carton detection.

You record each arm on its own with the normal single-arm software, then one command combines both recordings, checks the result and estimates its uncertainty.

Print, mount, measure→Camera intrinsics (optional)→Arm 1: 30–40 poses + touches→Arm 2: same→solve→Gate PASS?→Dual cell, with the recommended padding

Time: about 30 min of preparation, 1–1.5 h per arm, and 20 min for the intrinsics if you need them. Result: ~/dual_arm_calibration/dual_arm_calibration.yaml plus a report.

How it works
  • Arm boards. Each arm carries a small ChArUco board. The camera sees it in many poses, and the solver fits where the camera is relative to each arm's base. That gives arm 2's position through the camera.
  • Fit points. Both arms touch the same fit points with the knife tip: 4 crosshairs on the table board plus 4 stickers spread around it. That is a direct arm-to-arm measurement.
  • Check points. Both arms also touch 2 check stickers that are never used in any fit. The arm-to-arm disagreement there is the honest accuracy number.
The trust gate (8 checks) passes only if all of this is consistent.

verified in mock Every command in this guide ran end to end on 2026-10-08 in a mock setup with a simulated camera and a hidden "true" arm 2 position. The solver recovered it to 0.05 mm / 0.006°. Each deliberate fault failed the gate: a 5 mm check-point error, too few or too close touch points, touches only in the fit, and a 3 % camera focal-length error. Commands marked real hardware use hardware_protocol:=rebel and have not been run on the real robots yet.

What accuracy to expect

Two independent reviews and the literature agree on these limits for this cell:

  • Collision avoidance between the arms works with the padding the solver recommends: max(20 mm, 2 × worst check-point error + 10 mm).
  • At a work point about 0.4 m away, expect the two arms to disagree by roughly 7–10 mm typically, and 15–20 mm at worst. The robots run their nominal (uncorrected) kinematics, and these arms have joint zero errors, backlash and flex.
  • Not good enough for mm-level coordinated work, such as handing a part from one arm to the other. That needs kinematic correction or taught local corrections.
  • A PASS proves accuracy only where you measured it: at the check points. It does not prove it everywhere in the workspace.

Safety rules

Read before moving anything
  • Only one arm is connected and moving at a time during calibration. The single-arm software does not know the other arm exists, so park the other arm far away (folded, out of the shared workspace) before you move this one.
  • Ultrasonic knife OFF for the whole calibration. Keep a hand on the e-stop of the arm that moves.
  • In RViz always set Velocity and Acceleration scaling to 0.05 before planning. Plan first, look at the preview, then Execute.
  • Do not run iRC as the active CRI client while the ROS driver is connected.
  • Stop programs with Ctrl-C in their terminal. Never kill processes by name (pkill, killall).
  • A result whose gate did not PASS (source: calibrated_unverified) must not be trusted to keep the arms apart.

1. Prepare

Every terminal starts with these lines. Use the domain your real robot normally runs on (11):

source /opt/ros/humble/setup.bash

export ROS_DOMAIN_ID=11

2. Measure the prints

A 1 % print-scale error moves the camera result by about 10 mm at 1 m. Printers also scale the two paper directions differently, so measure the boards after gluing, in both x and y.

  1. Check the 50 mm scale bar on each page with calipers.
  2. On every board, measure across all squares in x (horizontal, as the labels read) and in y (vertical), from the first to the last outer square edge, then divide by the number of squares. Never measure a single square: 0.5 mm of caliper error on one square is a 1.4 % scale error.
    • Arm boards: 3 squares, nominal 105.0 mm in x and in y.
    • Table board: 5 squares in x, nominal 200.0 mm; 4 squares in y, nominal 160.0 mm. It prints landscape, so the printer's stretch may be on its y axis.
    Markers: scale the nominal marker size (26 mm on the arm boards, 30 mm on the table board) by the same factor per axis, e.g. 26 × 105.5 / 105 = 26.12 mm.
  3. If x and y differ by more than about 0.15 %, that's normal for printers, but do enter both values.
  4. Copy the default target file and enter your values in metres:
mkdir -p ~/dual_arm_calibration
cp $(ros2 pkg prefix rebel_dual_arm_calibration)/share/rebel_dual_arm_calibration/config/targets.yaml \
   ~/dual_arm_calibration/targets_measured.yaml
nano ~/dual_arm_calibration/targets_measured.yaml
# under arms.left, arms.right and table_board set, e.g. for 105.5 mm (x) and 105.0 mm (y) across 3 squares:
#   square_length: 0.0351667   (x)    square_length_y: 0.035     (y)
#   marker_length: 0.0261238   (x)    marker_length_y: 0.026     (y)

Pass this file to every recorder and UI launch (targets_file:=…/targets_measured.yaml). Each recording stores the sizes it used, so solve picks them up automatically. If a stretched print is slightly larger than its plate, trim the white margin; only the printed squares matter.

Don't change anything else in that fileThe marker IDs, square counts, touch points and sticker IDs must stay as they are.

2b. Knife-tip (TCP) calibration, per arm real hardware

The touches measure where the knife tip is, so the tip offset in the robot model (the TCP, igus_tool0 → xeg32_tool_tip) must be right first. The camera recordings (sections 6–7) do not depend on it. Method: pivot calibration — the tip sits in one fixed small dimple while the arm takes about 10 different orientations; the only tip offset that keeps the tip on that point in all of them is the TCP. Do it on the "0. TCP" tab of the calibration UI, for each arm, and again after any blade change.

Before you start
  • Ultrasonic OFF; only this arm connected, the other parked; a hand on the e-stop. The tab's buttons never move the robot; you position it with the teleop keyboard (or the jog panel).
  • Pivot fixture: a shallow countersink (about 2 mm deep, 90°) in a hard block (aluminium or steel; not PLA), clamped at working height inside the touch area.
  1. Start the stack as in 6.5 (driver, MoveIt with run_teleop:=true, the UI, the teleop keyboard) and open the 0. TCP tab. Tick the checklist (it resets on every page load).
  2. Caliper check: measure the flange face → blade tip along the flange axis and enter it. The current model implies 183.4 mm; an old pivot data set suggested ~168 mm — this tells us which is right.
  3. Fit poses (about 10) following the pose plan shown on the tab: knife vertical; tilted ±30° about two different axes; four combined tilts; two with the wrist rolled ±90° at 25° tilt. For each pose: lift the tip out of the dimple, rotate, re-seat it from above with light contact (do not rotate while the tip is in the dimple), release the keys, wait 2 s, Capture fit pose. A pose closer than 15° to an earlier one is refused.
  4. Validation poses (4), at different tilts, the same way with Capture validate pose. They are never used in the fit; they check it.
  5. Solve and read the verdict:
    VerdictMeaning / what to do
    GOODFit RMS ≤ 1 mm, max ≤ 2 mm, held-out OK.
    PASSFit RMS ≤ 2.0 mm, max ≤ 3.5 mm, held-out ≤ 2.5 mm, each direction ≤ 1 mm (1σ). Normal for this arm: its joint zero errors alone give ~1–1.5 mm.
    FAIL / INSUFFICIENTFollow the reasons: re-seat and re-capture a flagged pose (delete it first — nothing is deleted automatically), add tilts about the axis named, or add validation poses.
  6. Write result (GOOD / PASS only) saves tcp_result_<arm>.yaml in the session and shows a URDF diff. The UI never edits the robot model: review the diff, apply it to igus_rebel_xeg32_wrapper.urdf.xacro, rebuild igus_rebel_description and igus_rebel_moveit_config, restart the stack.
Touches recorded with the old TCPThey stay usable: pass the result to the solve and they are re-based automatically — solve … --tcp-file left=$HOME/dual_arm_calibration/left/tcp_result_left.yaml (and right=…). Without it, mixing touches recorded with different TCPs is refused.

The final proof of the TCP is the touch check later: the same crosshair touched with ≥ 25° different wrist tilts must agree (TCP consistency ≤ 1.5 mm), and the held-out check points must pass the trust gate.

4. Camera intrinsics (optional)

You can usually skip this step. By default the recorder uses the lens values the camera publishes itself (/camera/color/camera_info). solve then checks them against the recorded data (gate check intrinsics validated: focal length off by ≤ 0.3 %, centre by ≤ 3 px). Do this step only if that check fails, or if you want to rule the lens out in advance. A 1 % focal-length error moves the camera result by about 10 mm. No robot is needed.

If you skip it: leave out every intrinsics_file:=… and --intrinsics-file … line below. If the check fails later, do this step then (the camera must still be at the same place and resolution) and run solve again with --intrinsics-file; the arm recordings stay valid.

You hold the table board in front of the cameraDo this while the table board is not yet taped down, or hold a second print and cover the taped one. Never have two copies of the table board in view at once: they carry the same marker IDs.

Terminal 4, a recorder just for this step:

ros2 launch rebel_dual_arm_calibration record.launch.py mode:=single_left \
  output_dir:=$HOME/dual_arm_calibration/intrinsics_session \
  targets_file:=$HOME/dual_arm_calibration/targets_measured.yaml

Hold the board still for about 2 s at each view, then capture from terminal 5:

ros2 service call /dual_arm_calibration_recorder/capture_intrinsics std_srvs/srv/Trigger
  • Take 25–40 views. Cover the whole image: centre, all four corners and the borders.
  • Vary the distance from about 0.5 to 1.3 m, and tilt the board up to about 45° in different directions.
  • If a view is refused as "moving / blurred", hold steadier and capture again.

Then compute and read the result:

ros2 run rebel_dual_arm_calibration calibrate_intrinsics $HOME/dual_arm_calibration/intrinsics_session \
  --out $HOME/dual_arm_calibration/intrinsics.yaml

Good: RMS < 0.5 px, at least 25 views, and a coverage map without empty regions. The report also shows how far the factory values were off (Δf %, Δc px). Stop the recorder with Ctrl-C.

5. Place the table board and the stickers

Table board not ready yet?You can record the arm poses (6.3 and 7) first and do the table board and all touches later, as long as the camera and both arm bases have not moved. Later, start each arm's recorder again with the same output_dir (it resumes), then, before touching:
  • park the arm so it does not hide the table board and capture 3–5 times. The replies say NO ARM SAMPLE RECORDED (table-board image only …); that is expected here. These images give solve the camera-only loop check.
  • then do the touches (6.4) with that arm.
If something did move in between, the gate check camera vs touch fails; it does not pass silently.

6.2b Or: the calibration web UI

Instead of terminals 4 and 5 you can use the web UI. It starts the same recorder and adds a live camera view with the detected corners, pose and touch counters, buttons for capture and touches, and step-jog buttons. Use either the UI launch or record.launch.py, not both.

ros2 launch rebel_dual_arm_calibration calibration_ui.launch.py mode:=single_left \

# open exactly the URL the log prints: http://127.0.0.1:8095/?token=…  (new token at every start)
  • Tabs: Setup (session info, health checklist; every line must be green), Intrinsics (step 4, optional), Record arm (6.3, with Auto capture, below), Touches (6.4: pick the point ID, then Capture touch; done marks per arm). solve stays on the command line.
  • Jog panel: one small step per click (Cartesian 0.1–10 mm, rotation 0.5–5°, joint 0.5–5°), slow (≤ 10 mm/s), planned by MoveIt and checked for collisions. On the real robot it is locked until you press Enable motion and confirm the dialog (expires after 10 min idle or a page reload). STOP or Esc cancels the step. Keep a hand on the e-stop anyway: the knife tip has no collision model.
  • At a stretched-out arm pose Cartesian steps are refused; bend the elbow with a joint step first.
  • Auto capture (Record arm tab): switch it ON and just move the arm from pose to pose. Each time the arm has stood still for 2 s at a new pose (some joint at least 2° away from every pose already handled; 1° and 5° are selectable), it captures by itself and retries "board still moving" for up to 15 s. The same pose is not captured twice. The status line says what it is doing (waiting for a new pose, arm moving, settling, retrying, captured (n this run), same pose, skipped, gave up). It never moves the robot. It pauses during a jog step and switches off when you change tab or close the page; manual Capture is disabled while it is ON.

real hardware The UI and jog were verified on the mock stack only. On the first real session start with joint steps of 0.5°, then Cartesian 1 mm, with a hand on the e-stop.

6.3 Record 30–40 poses

For each pose: move the arm in RViz (drag the marker, Plan, check, Execute), let it stand still for at least 2 s, then capture:

ros2 service call /dual_arm_calibration_recorder/capture std_srvs/srv/Trigger

Read every reply. A refused capture records nothing.

ReplyMeaning
success=True, cap N: left: 20 corners (4 markers, 4 chess), PnP 0.2 px, sample #K; table board: …Good. 20 corners is the maximum for the 3×3 board; the recorder needs at least 8, and 16 or more is better.
arms not stationary yet (still for X s, need 2.00 s)Wait a moment and call again.
board still moving (common x px > 0.20 px, …)The arm stopped but the whole board still shifted between two images 0.4 s apart (plastic arm, bracket). Wait 1–2 s and call again (auto capture retries by itself). If it keeps happening, stiffen the board bracket. Normal pixel noise is not counted: only motion shared by all corners is. A capture that passes reports still (common … px, single max … px).
Message starts with NO ARM SAMPLE RECORDED (table-board image only …)The arm board was not seen (hidden, too oblique, or a duplicate pose). Move and capture again.
same pose as an existing sample, skippedChoose a different pose.

How to choose poses. Accuracy comes from variety:

  • Cover the whole area where the carton will be: near and far, left and right, low and high (about 10–30 cm above the table).
  • Tilt the board 20–45° in different directions (towards and away from the camera, left and right), and rotate the wrist (joint 6) between poses. Aim for at least 30° of variation in each direction across the set.
  • Keep the board fully visible and not edge-on to the camera (less than about 55° from facing it). The arm must not cover it.
  • Use 30–40 good samples. Fewer than 20 gives a warning.
  • Check the count anytime with status (samples left N).

6.4 Touches

Touch every point with the knife tip, set its ID, and record:

IDsWhereRole
1, 2, 3, 4Crosshairs on the table board (where four squares meet)Fit
101, 102, 103, 104Fit stickers around the boardFit (widens the rotation estimate)
111, 112Check stickers (block, and far point)Held-out: never used in the fit; this is the accuracy check

For each point do 2–3 touches, tilting the wrist by at least 25° between repeats. That also checks the knife-tip (TCP) position. Always approach from above in the same way, so gear backlash is the same each time.

  1. In RViz, bring the knife tip to about 10 mm above the point, at scaling 0.05.
  2. Come down in small steps until the tip just touches the crosshair centre (the 1 mm ring on the stickers). Don't press: the arm flexes. For fine steps use the web UI's jog panel (0.5 mm, then 0.1 mm), or restart MoveIt with run_teleop:=true and use the keyboard teleop at its smallest step.
  3. When the arm is still, select the point and record:
ros2 param set /dual_arm_calibration_recorder touch_point_id 101
ros2 service call /dual_arm_calibration_recorder/capture_touch std_srvs/srv/Trigger
  1. Lift the tip about 10 mm before the next touch. Go through all 10 IDs, setting touch_point_id each time.
  2. Optional, for a repeatability number (ISO 9283 style): touch one sticker 5 times at the same wrist orientation, lifting 10 mm in between.

In the web UI: select the ID on the Touches tab and press Capture touch instead of the two commands.

A wrong touch?Stop the recorder (Ctrl-C), delete that line from ~/dual_arm_calibration/left/touches.jsonl, and start the recorder again with the same command. It resumes and keeps the existing samples.

When done: run status once more, then stop the recorder, MoveIt and the driver with Ctrl-C (terminals 4, 3, 2). Leave the camera running.

6.5 Touching the table crosshairs with the hover assist real hardware

The camera finds the table board, the calibration predicts where crosshairs 1–4 are for this arm, and the arm is sent to 60 mm above the chosen crosshair with the knife pointing straight down. You bring the tip down the last few centimetres with the teleop keyboard and record the touch. The UI then shows predicted vs touched: how far the real crosshair was from where the calibration thought it was. That number is the honest accuracy of the camera-to-arm calibration at that point.

Before you start
  • Knife covered, ultrasonic off, a hand on the e-stop of the moving arm. Only this arm is connected; the other one is parked out of the way.
  • MoveIt Servo (the teleop) has no collision checking in this setup, and the knife tip has no collision model anywhere: only you keep it off the board.
  • Never press a UI motion button while a teleop key is held. The UI refuses to start a motion while the arm moves ("the arm is moving (teleop active?)").
  • The table board is fixed and must not move until both arms have done their touches.

8. Solve and read the gate

Nothing moves in this step. It takes about 20 s, plus about 1 minute for the uncertainty estimate.

ros2 run rebel_dual_arm_calibration solve \
  $HOME/dual_arm_calibration/left $HOME/dual_arm_calibration/right \
  --out $HOME/dual_arm_calibration/dual_arm_calibration.yaml \
  --intrinsics-file $HOME/dual_arm_calibration/intrinsics.yaml \
  --uncertainty-mc 200

Skipped step 4? Leave out the --intrinsics-file line.

Also read these in the report:

  • Check points: the arm-to-arm error at 111 and 112. This is the number to quote.
  • Recommended padding (recommended_padding_mm): use at least this between the arms in MoveIt.
  • Uncertainty budget: 95 % ranges for arm 2's position and for the arm-to-arm disagreement at three workspace points. It includes print scale, lens, knife-tip offset, touch noise and joint zero errors.
  • Repeatability, if you did the 5-repeat touches: RP in mm per arm. It should be near the ±1 mm specification.

9. If the gate FAILs

The YAML is still written, with source: calibrated_unverified. Don't rely on it to keep the arms apart. Find the cause:

Failing check / symptomLikely causeFix
common touch points or check-point coverageA point was missed on one arm, or a different ID was usedTouch the missing IDs with that arm (restart its recorder with the same folder; it resumes), then solve again.
touch geometryThe fit stickers are too close together, or there are too few repeatsSpread stickers 101–104 wider (then re-touch them with both arms), and do 3 touches per point.
check-point error > 3 mm while the fit looks goodJoint zero errors or flex in the arms; the error grows away from the boardTry the --joint-offsets solve. Otherwise adjust the joint zero offsets in iRC and re-record, or accept a larger padding (the report's recommended_padding_mm).
TCP consistency > 1.5 mm (in the report)Wrong knife-tip offset, or a loose bladeTighten the blade, re-check the TCP calibration, and redo the touches.
held-out validation, or a large RMS pxThe camera, board or stickers moved between arms; print size not entered; wobbly board bracketCheck nothing moved, measure the print, stiffen the bracket, re-record.
intrinsics validatedNo intrinsics file, and the factory lens values look offDo step 4 and pass --intrinsics-file.
camera vs touchOne of the two methods is biased (lens, print scale, TCP)Check the intrinsics, print measurements and TCP consistency first.

10. Use it in the dual cell

Before the first dual-arm run The installed driver must be rebuilt first, so it includes the two-arm and fault-group support (commits 374935a, 11f1c4d). Ask for this to be done. When the dual launch starts, its log must show Joined fault group 'dual_arm_table' for both arms.
ros2 launch rebel_dual_table_description dual_table.launch.py hardware_protocol:=rebel \
  left_robot_ip:=192.168.3.11 right_robot_ip:=192.168.3.12 \
  calibration_file:=$HOME/dual_arm_calibration/dual_arm_calibration.yaml

ros2 launch rebel_dual_table_moveit_config move_group.launch.py hardware_protocol:=rebel use_gui:=true \
  calibration_file:=$HOME/dual_arm_calibration/dual_arm_calibration.yaml

11. Re-checks

After every robot power cycle or re-homing, a joint-1 zero shift turns directly into an error in arm 2's position. Both arms touch the two check stickers again in short recordings (sections 6–7 with new folders, touches only), then:

ros2 run rebel_dual_arm_calibration check_points \
  $HOME/dual_arm_calibration/left_recheck $HOME/dual_arm_calibration/right_recheck \
  --calibration $HOME/dual_arm_calibration/dual_arm_calibration.yaml

The error must stay within the gate limit of 3 mm. Nothing is fitted in this step. The check stickers must still be exactly where they were.

Reproducibility: repeat the full calibration on another day and compare it with the previous result. Accept when arm 2's base changed by less than 2 mm / 0.2°.

ros2 run rebel_dual_arm_calibration solve …new sessions… --out new.yaml \
  --compare $HOME/dual_arm_calibration/dual_arm_calibration.yaml

Troubleshooting

Message / symptomWhat to do
newest image is X s old (max 1.0 s)The camera isn't delivering. Check ros2 topic hz /camera/color/image_raw, and restart the camera launch if needed. If it happens only sometimes, large 1080p frames are being dropped by the ROS transport.
no image / camera_info received yetThe camera isn't running, or is on a different ROS_DOMAIN_ID.
newest image predates the stationary window / no earlier image …Call capture again after holding still.
TF base->tip is stale/unavailableThe robot stack isn't running (or another domain). Check ros2 run tf2_ros tf2_echo base_link link6.
left: not detected / only N cornersThe board is hidden, too oblique, too far, or glare. Tilt it more towards the camera.
PnP reprojection … rejectedBlurry or partly hidden board. Wait longer before capturing, or pick another pose.
solve exits with code 2 naming two sessionsThe two recordings used different camera settings (resolution or intrinsics). Re-record one arm with the same camera configuration.
board still moving (common …) on almost every try, even after standing still for 10 sThe camera's pixel noise is higher than expected (dim light, flicker). Add light first. If it persists, restart the UI / recorder with the same output_dir plus max_corner_motion_px:=0.3 (default 0.2); note the "common" values you saw.
Arm 2 shakes or overshootsStop. Its controller gains were tuned on arm 1; this needs a gain check before continuing.
